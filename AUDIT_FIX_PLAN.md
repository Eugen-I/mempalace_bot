## 2. Правила изменения кода

1. **Один шаг = одно логическое изменение + тесты + один коммит.**
2. Сначала воспроизведи баг тестом (RED), затем чини. Если тест сразу зелёный — он не проверяет баг, перепиши.
3. Минимальное изменение: не переписывай модуль целиком, если достаточно локального фикса.
4. Не делай массовый реформат и не меняй стиль чужих строк «заодно».
5. Новый код — с типами и понятными именами. Публичные функции — с docstring, если это принято рядом.
6. Не меняй публичный API без обновления всех вызовов, тестов и документации.
7. **Запрещено подгонять тесты**: нельзя удалять/скипать/ослаблять корректный тест, чтобы он прошёл. Если тест закрепляет баг (например, `safe_html_format`), обнови тест осознанно и объясни это в журнале.
8. Если для фикса нужна новая зависимость — сначала проверь, есть ли уже подходящая; затем обнови **и** `pyproject.toml`, **и** `requirements.txt`.
9. Для async-кода: не вызывай блокирующие функции в event loop. Используй `asyncio.to_thread`/асинхронный клиент, таймауты и отмену.
10. Для пользовательских функций: если бэкенда нет, не показывай фальшивый успех. Либо реализуй реально, либо убери/скрой кнопку и явно сообщи о недоступности.
11. Не оставляй после шага сломанный импорт, падающий тест или незакоммиченный мусор.
12. Соблюдай `AGENTS.md`, включая anti-gaming и debugging-протокол. Для этой работы источник истины по прогрессу — `AUDIT_FIX_PROGRESS.md`; `TESTING_PROGRESS.md` можно дополнять только краткой ссылкой, не дублируя журнал.

## 3. Протокол выполнения одного шага

### 3.1. До начала

1. Открой журнал и запиши в «Текущий снимок»:
   - дату/время, ветку, `HEAD`, ID шага;
   - статус `IN_PROGRESS`;
   - оценку бюджета (из карточки шага).
2. Проверь `git status --short`. Если есть незакоммиченные изменения не от тебя — не трогай их; зафиксируй в журнале.
3. Прочитай якорные файлы и существующие тесты. Не полагайся только на отчёт аудита.
4. Сформулируй в журнале гипотезу/план в 1–3 строках.

### 3.2. Во время работы

- Держи изменение в рамках шага. Если обнаружил соседний баг — не чини его здесь, создай запись в разделе «Найдено попутно» журнала.
- Сначала тест, потом фикс.
- Следи за бюджетом: см. раздел 4.
- Если после двух попыток фикс не сходится — остановись, запиши 2–3 гипотезы с вероятностями, статус `BLOCKED`.

### 3.3. После работы

1. Запусти проверки (раздел 5). Для P0/P1 и общих модулей — полный `make qa`. Для документации/чистки — минимум, но с обоснованием в журнале.
2. Убедись, что новые тесты падали на старом коде (кроме случаев, где это невозможно; объясни).
3. Обнови журнал:
   - статус `DONE`/`BLOCKED`/`PARTIAL`;
   - commit hash;
   - файлы;
   - команды и результат;
   - фактический/оценочный расход токенов;
   - AC-чеклист;
   - что осталось.
4. Сделай один коммит:
   ```bash
   git add <только файлы шага>
   git commit -m "fix(step-ID): краткое описание"
   ```
   Для рефакторинга — `refactor(step-ID): ...`, для тестов/чистки — `test(step-ID): ...` / `chore(step-ID): ...`.
5. Только после коммита и записи в журнал переходи к следующему шагу.

## 4. Лимит токенов и handoff

**Жёсткий лимит одного шага — 50 000 токенов.** Целевой бюджет — 15–35k.

Правила:

- Если на старте видно, что шаг не влезет в 40k, **сразу раздели его** на `Sx.y-a`/`Sx.y-b` и зафиксируй в журнале.
- Если израсходовано ~40k или контекст заполнен на ~80% — остановись на безопасной точке.
- Не начинай новый шаг, если осталось меньше ~15k токенов.
- Точный расход может быть недоступен; веди консервативную оценку по объёму прочитанного/записанного и указывай «оценка».
- При остановке обязательно заполни `HANDOFF` в журнале:
  - шаг и статус (`PARTIAL`);
  - ветка/HEAD;
  - `git status` и изменённые файлы;
  - что уже работает;
  - что не проверено;
  - **точное следующее действие** (1–3 команды/правки);
  - риски и что нельзя делать.
- Не коммить заведомо сломанное состояние. Если нужно сохранить WIP, делай коммит только с явной пометкой `wip(step-ID): ...` и записывай, что он не проходит QA.
- При возобновлении: прочитай handoff, проверь `git status`, `git log`, `git diff`, прогони targeted-тесты, продолжи с указанного действия. Не начинай шаг с нуля.
