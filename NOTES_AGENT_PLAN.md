> Инструкция для агента (VS Code Insiders). Проект: `mempalace_bot`.
> Хранилище памяти (Дворец): `~/projects/mempalace` — отдельный MCP-сервер, уже
> интегрирован через `services/palace_mcp.py`. НЕ путать с Apple Notes.
>
> Текущее состояние (проверено чтением кода 2026-08-10):

## Договорённости с пользователем (зафиксировано в диалоге)

1. Кнопка «📝 Заметки» — отдельный вход в режим работы ТОЛЬКО с Apple Notes
   (без Дворца/MCP-памяти), плюс агент должен САМ предлагать сохранить/прочитать/
   проанализировать заметку из обычного контекста диалога (не только по кнопке).
2. Набор операций (в порядке приоритета реализации):
   - создание заметки (`notes_create`)
   - поиск/чтение (`notes_search`, `notes_read` — уже есть)
   - обновление/дополнение текста (`notes_append` или `notes_update`)
   - удаление — **только с двойным подтверждением** (`notes_delete`)
   - работа с папками (`notes_list_folders`, возможно `notes_move`)
   - просмотр списка последних заметок (уже есть `notes_list`, добавить сортировку по `updated`/последним изменениям)
3. Модель и бот работают на этом же Mac — прямой вызов AppleScript/JXA без туннелей.
4. Подтверждение — **всегда** для любых write-действий (создание/обновление/папки),
   **двойное** — для удаления (два разных «Да», второй с явным текстом
   «Подтвердите ещё раз: удалить безвозвратно?»).
5. Язык заметок: русский (основной) и немецкий (иногда) — автоопределение языка;
   **явный запрет** на китайский/японский/корейский и другие азиатские скрипты
   (валидация по Unicode-диапазонам перед созданием/обновлением заметки).

## Архитектурное решение (соответствует существующим конвенциям)

Telegram user
→ handlers/notes_agent.py (НОВЫЙ) — кнопка «📝 Заметки», команда /notes_agent
или авто-предложение из handlers/agent.py при обнаружении intent
→ services/agent_engine.run_agent(include_write=True при подтверждении,
allowed_categories=(CAT_NOTES,))
→ services/agent_tools.py (реестр, allowlist)
→ services/agent_notes_tools.py (READ, уже есть)
→ services/agent_notes_write_tools.py (НОВЫЙ, is_write=True)
→ services/apple_notes.py (добавить create_note/update_note/
delete_note/list_folders/move_note)
→ AppleScript-мост (JXA), TCC-разрешения уже настроены


Ключевой принцип безопасности проекта — **write-инструменты никогда не выполняются
моделью напрямую**. Модель только предлагает вызов (`tool_call`), хендлер бота
перехватывает его, показывает пользователю карточку подтверждения, и только
после нажатия «✅ Да» реально вызывает `apple_notes.create_note(...)` и т.п.
То есть цикл `run_agent` для write-операций работает в **два прохода**:
первый — без выполнения записи (агент формирует план), второй — после
подтверждения (реальное выполнение). Это НЕ то же самое, что `include_write=True`
на старте — такой флаг гонял запись без остановки. Нужно новое поведение
"pending write" — см. Фазу 2 ниже.

## ФАЗА 2 — Механизм подтверждения (pending-write) в хендлере

Это ключевая и самая тонкая часть — здесь нельзя просто выставить
`include_write=True`, потому что тогда модель выполнит запись без паузы
на подтверждение. Нужен перехват tool_call ДО его выполнения.

### Шаг 2.1 — Модифицировать `services/agent_engine.py`
- Добавить необязательный параметр `confirm_write: Callable[[str, dict], Awaitable[bool]] | None`
  в `run_agent()`. Когда движок собирается выполнить инструмент с `tool.is_write=True`,
  ПЕРЕД вызовом `atools.execute_tool(...)`:
  - если `confirm_write` не передан — вести себя как сейчас (не давать write-тулы,
    т.е. оставить `include_write=False` по умолчанию — обратная совместимость);
  - если передан — вызвать `await confirm_write(tool.name, call["arguments"])`;
    если он вернёт `False` — вставить в `messages` результат tool с текстом
    «Пользователь отклонил действие», НЕ выполняя реальный вызов, и продолжить
    цикл (модель должна вежливо остановиться/предложить альтернативу).
- Это позволяет сохранить единый `run_agent()` без дублирования кода цикла.

### Шаг 2.2 — Хендлер: `handlers/notes_agent.py` (НОВЫЙ файл)
- По образцу `handlers/agent.py`, но с:
  - системным промптом `NOTES_AGENT_SYSTEM_PROMPT` — сузить контекст ТОЛЬКО на
    заметки (без Дворца), явно прописать правило автоопределения языка и
    запрет на азиатские языки, а также правило «всегда объясняй, что собираешься
    сделать, перед вызовом write-инструмента»;
  - `allowed_categories=(CAT_NOTES,)` и `include_write=True` (запись доступна,
    но реально гейтится через `confirm_write` из Фазы 2.1);
  - реализацией `confirm_write`, которая:
    1. Формирует карточку в Telegram: «Хочу выполнить: `notes_create` — заголовок
       X, текст Y. Подтвердить?» с кнопками `notes_confirm:<token>` / `notes_cancel:<token>`.
    2. Для `notes_delete` — ДВА последовательных подтверждения: первая карточка
       («Удалить заметку "X"?») → при «Да» — вторая карточка («Это необратимо.
       Подтвердите ещё раз: удалить безвозвратно?») → только тогда `True`.
    3. Приостанавливает `run_agent` (через `asyncio.Event` или future, сохранённый
       в `TtlDict`, по аналогии с `_remind_pending` в `reminder.py`) до нажатия кнопки.
    4. Таймаут ожидания подтверждения (например, 120с) — если пользователь не
       ответил, вернуть `False` и сообщить об истечении времени.
- Обработчики `cb_notes_confirm` / `cb_notes_cancel` (`@router.callback_query`,
  `@allowed_callback`) — resolve pending future/Event с результатом `True`/`False`.

### Шаг 2.3 — Кнопка «📝 Заметки» в главном меню
- Открыть `services/menu.py` — добавить кнопку рядом с существующими

- Следующее текстовое сообщение пользователя в этом режиме — направляется в

### Шаг 2.4 — Авто-предложение из обычного диалога (без кнопки)
- В `handlers/messages.py` (посмотреть текущий гейт `agent_enabled`) добавить
  лёгкую классификацию intent: если сообщение похоже на «сохрани это», «найди
  мою заметку про...», «что там в заметках про...», «прочитай заметку X» —
  предложить кнопку «📝 Работать с заметками?» вместо неделенного запуска

  regex/keyword-эвристику НЕ через отдельный LLM-вызов (дёшево и предсказуемо),
  либо через уже работающий общий агент (`AGENT_SYSTEM_PROMPT`), который сам

  работает, так как `notes_read`/`notes_search` доступны агенту в read-режиме.
  Write-предложения («хотите сохранить это как заметку?») — новая логика,
  разместить в `handlers/notes_agent.py` как функцию
  `maybe_suggest_note_action(text) -> str | None`, вызываемую из `messages.py`.

---

## Комбинации приёмов для сюрреализма (проверено на реальных примерах)

Настройки камеры можно и нужно комбинировать между собой — совмещение
режима съёмки (мультиэкспозиция, длинная выдержка) с эмуляцией плёнки и
экстремальными сдвигами цвета/баланса белого даёт более сильный
сюрреалистичный эффект, чем один приём отдельно. Ниже — два разбора
реальных подходов сообщества Reddit.

### Комбо 1 — Мультиэкспозиция + разные эмуляции плёнки на каждый слой

Пример с Reddit: фотограф снял серию двойных экспозиций на X-T30 II, где
для цветных кадров использовалась эмуляция Классический Негатив, а для
чёрно-белого кадра — ACROS, при этом между экспозициями сознательно менял
баланс белого, чтобы усилить контраст между слоями [web:182]. Другой автор
делал монохромные двойные экспозиции в Каппадокии на основе рецепта,
вдохновлённого ACROS ("Grain Noir") — все кадры SOOC, без пост-обработки
[web:180].

**Как повторить на X-T4:**
1. `НАСТРОЙКА СЪЕМКИ → МУЛЬТИЭКСПОЗИЦИЯ → ВКЛ`, режим наложения — DARK
   (сравнительно тёмный) — второй слой проявляется только в светлых
   участках первого [web:186].
2. Первый кадр: имитация плёнки Классический Негатив, ДД200, Зерно
   Сильное/Крупное, Цв.хром Сильный — снять силуэт или контражурную сцену.
3. МЕЖДУ кадрами сменить имитацию плёнки на ACROS (монохромная), сдвинуть
   Баланс белого на противоположный знак (например, было R+4 B-4 → стало
   R-4 B+4) — камера сохранит переключение и применит его ко второму слою.
4. Второй кадр: снять текстуру/узор (листва, вода, окно) в том же
   ракурсе — результат: цветной силуэт "прорастает" монохромной текстурой.

**Почему это сюрреалистично:** смена и эмуляции, и баланса белого между
слоями создаёт визуальный конфликт "двух разных фотографий из разных
миров", наложенных в одном кадре — эффект невозможен при односложной
съёмке.

### Комбо 2 — Экстремальный сдвиг ББ + сильное зерно + ACROS (статичный кадр)

Пример из подтверждённого рецепта "Kodak Tri-X" для X-Trans IV: имитация
ACROS, Цветной хром-эффект Сильный, Баланс белого Дневной с максимальным
сдвигом R+9 B-9 (предельные значения шкалы), Зерно Сильное/Крупное,
Динамический диапазон DR200, Тон.кривая Тень +3, Прозрачность +4,
ISO auto от 1600 [web:121][web:154].

**Как повторить на X-T4:**
1. Имитация плёнки: ACROS (без цветного фильтра — чистый монохром).
2. Баланс белого: Дневной свет, сдвиг R+9 B-9 (крайние значения ползунка —
   несмотря на монохромную имитацию, сдвиг ББ влияет на тоновый рендеринг
   зон изображения через цветной хром-эффект).
3. Цветной хром-эффект: Сильный (усиливает разделение тонов в тенях).
4. Зерно: Сильное, Крупное — визуально "рвёт" гладкость кадра, добавляя
   фактуру, похожую на явно нереальную, "выжженную" плёнку.
5. Прозрачность: +4 (максимум) — неестественно резкие микро-контрасты,
   выглядящие почти графично, а не фотографично.

**Почему это сюрреалистично:** комбинация предельных значений ББ-сдвига
(которые в теории должны быть "невидимы" в чистом ЧБ) с максимальной
Прозрачностью и крупным зерном создаёт эффект "потустороннего" контраста —
кадр выглядит одновременно фотографично и графически искажённо, что
типично для сюрреалистичной эстетики.

### Общее правило смешивания (для агента)

Любые ДВА параметра из разных категорий можно комбинировать без риска
"сломать" JPEG-обработку камеры: (режим съёмки: мульти-экспозиция/длинная
выдержка) + (имитация плёнки) + (экстремальный ББ-сдвиг ИЛИ экстремальная
Прозрачность/Зерно). Не рекомендуется комбинировать более 3 экстремальных
параметров одновременно — результат становится непредсказуемым даже для
опытных пользователей Reddit, что подтверждается отсутствием таких
рецептов в проверенных источниках.
